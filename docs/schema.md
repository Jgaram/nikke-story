# 데이터 스키마

원본 JSON(`data/raw/`)을 질의 가능한 형태(`data/normalized/`, `data/nikke.db`)로 옮길 때의 계약.

## 설계 원칙

1. **게임 원본 분류와 사람 분류를 둘 다 보존한다.** 데이터상 이벤트·퀘스트·사이드는
   전부 아카이브에 섞여 있다. 시트의 유형 구분은 사람이 붙인 것이므로 별 칼럼으로 둔다.
   **시트는 참고자료다** — 시트 칼럼(`sheet_type`·`importance`·`accessibility`·`release_date`)과
   `origin='sheet'` 엣지는 비교용으로 연결만 해 둔 값이고, 분석의 입력이나 정답이 아니다 (CLAUDE.md).
2. **원문이 없는 노드도 1급 시민이다.** 아카이브X 이벤트, 사이드, 애장품은 대사가 없지만
   관계 그래프에는 반드시 올라야 한다. `has_text`로 구분한다.
3. **관계에는 출처를 남긴다.** 게임 데이터에서 온 것, 시트에서 온 것, 자동 추론한 것,
   사람이 직접 쓴 것을 섞지 않는다 (`edges.origin`).
4. **ID는 `scenario_group_id` 계열을 그대로 쓴다.** 숫자 id는 카테고리마다 중복된다.

## ID 규칙

| 접두 | 대상 | 예 |
|---|---|---|
| (없음) | 씬 | `d_main_01_01_s`, `d_ex_gym_01`, `event_nocallerid_01_s` |
| `ep:` | 호감도 스토리 (니케별 개인 스토리 5편, 데이터 `episode`) | `ep:d_nikke_emma_01` |
| `fav:` | 애장품 | `fav:200101` |
| `sheet:` | 시트에만 있는 이름 (원문 없음, 참고용) | `sheet:second-quest`, `sheet:bullet-x-chainsaw` |
| `fl:` | **금서고**: 블라링크에 원문이 없는 이벤트 (단위 · 씬) | `fl:absolute`, `fl:absolute_03` |
| `side:` | **금서고**: 사이드 스토리 | `side:mudfish`, `side:mudfish_00` |
| `sub:` | **금서고**: 서브퀘스트(메신저 · 퀘스트 대화) | `sub:칠리페퍼`, `sub:칠리페퍼_01` |
| `relic:` | **금서고**: 유실물(문서) | `relic:어느남자의수기`, `relic:어느남자의수기_00` |
| `erelic:` | **금서고**: 이벤트 유실물(필드 대화 · 미니게임 스토리 · 이벤트 유실물) | `erelic:old_tales_dialog_00` |

금서고 키는 `<접두>:<금서고 파일 이름>`이 단위, 끝에 `_NN`(파일 안 순서, 0부터)을 붙이면 씬이다.
게임 씬 ID가 아니다 — 금서고 원문에는 게임 ID가 없다. 금서고 자체 ID(`SCRIPT_ID`)는 `stories.source_ref`에 둔다.
블라링크에 원문이 새로 들어오면 `annotations/forbidden-library-events.json`으로 이어 블라링크 쪽으로 돌아간다
(CLAUDE.md "금서고 요청 규칙").

씬 ID는 **대소문자를 구분한다.** `event_BunnyX777`이 실존한다 —
정규식을 `[a-z0-9]`로 짜면 통째로 빠진다.

## 대상 ID — 인물 · 장소 · 조직 · 개념 · 사건 · 물건 (A1 · A2)

스토리에 나오는 대상(언급 DB T3-9의 "대상", 사전 T2-6 · T3-2)의 ID는 **`<종류>:<표준명>`** 이다.
표준명의 공백은 `_`로 바꾸고 다른 글자는 그대로 둔다. 씬 ID · 단위 키와 접두가 겹치지 않는다.

| 접두 | 종류 | 예 | 채우는 곳 |
|---|---|---|---|
| `person:` | 인물 — 니케 · 사람 · 랩쳐 · 헬레틱 · AI · 메신저 대화명 등 이름 있는 개체 | `person:라피` `person:스노우_화이트` `person:T.A.L.O.S.` | A1 |
| `place:` | 지역 · 장소 (탈것 포함) | `place:방주` `place:아우터_림` `place:어드마이어_호` | A2 — `places.json` |
| `org:` | 조직 · 세력 (기업 · 정부 · 스쿼드 · 단체) | `org:중앙_정부` `org:카운터스` `org:A.C.P.U.` | A2 — `orgs.json` |
| `concept:` | 개념 · 설정 (존재 · 등급 · 랩쳐 종류 · 기술 …) | `concept:랩쳐` `concept:NIMPH` `concept:타일런트_급` | A2 — `concepts.json` |
| `incident:` | 사건 (전쟁 · 작전 · 테러) | `incident:랩쳐_침공` `incident:2차_지상_탈환전` | A2 — `incidents.json` |
| `item:` | 물건 (장치 · 무기 · 문서) | `item:하모니_큐브` `item:세븐스_드워프` | A2 — `items.json` |

- **한 번 정한 ID는 바꾸지 않는다.** 표준명이 바뀌면 `targets.name`만 고친다. 기록(후보 · 언급)이 ID로 가리키기 때문이다.
- **동명이인**은 뒤에 `_구분어`를 붙인다: `person:사쿠라`(TETRA, rid 282 · 284) / `person:사쿠라_콜라보`(ABNORMAL, rid 836).
- 니케는 니케 목록(`characters`)의 **앞 이름**으로 묶는다: `라피`(rid 10)와 `라피 : 레드 후드`(rid 16)는 `person:라피` 하나다.
  `레드 후드`(rid 470)는 앞 이름이 달라 다른 인물이다.
- 정체가 나중에 밝혀지는 인물(모더니아 ↔ 마리안, 대화명 ↔ 본명 등)은 **따로 두고** 정체 연결 후보(`target_links`)로 잇는다.
  확정 · 기각은 Claude가 그 단위를 읽을 때 하고, 사용자는 언제든 뒤집는다(CLAUDE.md "해석이 필요한 기록").
- 사전 파일: `annotations/dictionary/people.json`(손으로 정한 인물 · 후보) · `annotations/dictionary/speakers.json`(이름표 분류) ·
  비인물은 종류별 `places.json` · `orgs.json` · `concepts.json` · `incidents.json` · `items.json`(아래 "비인물 사전").
  빌드는 `tools/normalize/dictionary.mjs`. 조회는 `node tools/query.mjs who 라피` · `node tools/query.mjs terms`.
- 비인물 ID는 표준명에서 만든다(테스트가 본다). 표준명을 나중에 바꾸면 ID는 그대로 두고 항목에 `idNote`로 까닭을 적는다.

| `window` | 뜻 | 줄 수 |
|---|---|---:|

이 게임의 서술자는 3인칭(`Narration`)이거나 지휘관 1인칭(`Monologue`)이다. 이름표는 서술자가 아니라
대사를 말한 인물이다. 그래서 이름표만으로는 말없이 서술 속에만 나오는 인물을 잡지 못한다.

**가짜 이름표**: 원본은 `speaker` 칸에 창 종류(`Self`/`Monologue`/`Narration`/`Choice`)를 그대로 넣기도 한다
(13,155줄). 사람이 아니므로 `speaker_id`에서 빼고 `window`로만 남긴다.

**분기 읽는 법**: 선택지 줄의 `jump_to`는 그 선택의 응답이 시작하는 줄이다. 선택지가 아닌 줄에 `jump_to`가
있으면 그 분기의 끝이고, 합류 지점으로 건너뛴다(1,728줄). 분기가 없으면 `seq` 순서대로 읽는다.

### `characters`

`resource_id`가 PK다. **이름은 충돌한다** — `사쿠라`가 rid 282(니케)와 836(콜라보) 둘이다.
`target_id`는 인물 대상이다 — 같은 인물의 다른 판(`라피 : 레드 후드`)은 같은 대상(`person:라피`), 동명이인은 다른 대상.

### `targets` · `target_names` — 대상 사전 (A1 인물 · A2 비인물)

| `targets` 칼럼 | 설명 |
|---|---|
| `id` | 대상 ID (위 "대상 ID") |
| `type` | `person` · `place` · `org` · `concept` · `incident` · `item` |
| `name` | 표준명 |
| `kind` | 갈래 — 인물: `니케`(니케 목록에 있음) · `인물` · `랩쳐` / 비인물: 사전 파일에 적은 것(`도시` · `기업` · `스쿼드` · `존재` · `작전` …) |
| `resource_ids` | 니케 목록 resource_id들(JSON 배열) |
| `origin` | 어디서 만들어졌나: `니케 목록` · `이름표`(speakers.json의 인물 · 랩쳐) · `사전`(people.json · 비인물 사전 파일) |
| `note` | 메모 · 근거 |
| `lines_in_scope` · `stories_in_scope` | 이름 중 하나가 나온 범위 안 대사 줄 수 · 씬 수 — 비인물은 "비인물 사전" 검색 규칙, 인물은 언급 DB 자동 줄에 쓴 이름("언급 DB", B2) |

`target_names`(`target_id` · `name` · `how` · `caution` · `excludes` · `lines_in_scope`)는 대상의 이름들이다.
`how`: `표준명` · `니케 목록`(다른 판 이름 `라피 : 레드 후드`) · `정식 명칭` · `약칭` · `별칭` · `표기`(띄어쓰기 · 문장부호만 다름) · `영문` · `이명`.
`caution`은 오탐 주의 사유, `excludes`는 검색에서 뺄 더 긴 표기(JSON 배열 — 인물은 표본 정밀도 파일의 `except`), `lines_in_scope`는 그 이름 하나의 범위 안 줄 수,
`mention_mode` · `precision`은 언급 DB 자동 줄에 쓰는 법(`all` · `unit` · `off`)과 표본 정밀도(아래 "언급 DB").
인물의 별칭 · 이명은 읽기 세션이 더한다. **이름표는 여기 넣지 않는다** — 이름표 → 대상은 `speakers`에 있다
(`억울한 지휘관` 같은 이름표는 본문 검색용 이름이 아니다).

2026-09 빌드: 대상 458 — 인물 366(니케 156(니케 목록 202행 → 앞 이름 155 + 콜라보 사쿠라) · 인물 200 · 랩쳐 10(이름표 9 + A2의 `person:퀸`)) ·
비인물 92(장소 19 · 조직 47 · 개념 16 · 사건 7 · 물건 3, 이름 131).

### `speakers` — 이름표 분류 (A1)

이름표 한 종류 = 한 행. 칸: `name`(이름표) · `class`(갈래) · `targets`(대상 ID JSON 배열) · `how`(`니케 목록` = 니케 목록 이름 그대로 ·
`분류` = speakers.json · `모호` = 동명이인이라 못 풂) · `note` · `lines` · `lines_in_scope` · `code_lines`(코드 규칙으로 푼 줄). 규칙은 아래 "이름표 분류".

### `target_links` — 정체 연결 후보

`annotations/dictionary/people.json`의 `candidates`. 칸: `id`(후보 ID `L<n>` — 리뷰 도구가 이 ID로 확정 · 기각한다, docs/annotations.md) · `type`(`same_as`) · `a`(대상 ID, 또는 대상 없는 이름표 `이름표:곰…?`) · `b`(대상 ID) ·
`status`(`후보` · `확정` · `기각`) · `confidence`(`확실` · `추정`) · `reason` · `evidence`(JSON `[{scene, lines}]` — 비면 1회독이 채운다) · `recorder`(기록자).
Claude는 후보만 쓰고 확정 · 기각은 사용자가 한다. 확정 · 기각은 `node tools/records.mjs set L3 확정`으로 적고(`reviews`에 누가 · 언제가 남는다),
1회독 기록(사실 · 의문 · 시점 후보, `annotations/read1/`)과 같은 리뷰 도구로 본다 — 형식은 [annotations.md](annotations.md).

### `edges` — 관계

**방향은 읽는 순서다.** `from`을 먼저 보면 `to`를 이해할 수 있다.
선행 조건 "B를 보려면 A가 필요"는 `from=A, to=B`로 들어간다.

**DB `edges`에는 빌드가 원본에서 바로 아는 것만 둔다**(X2, 2026-10-08 — Claude): 게임 조건(호감도 스토리 `prereq` · 애장품 `character`)과 시트 참고(`sheet`).
관계선 전체(다음 편 · 기록 · 대상 공유 · 수동)는 DB에 싣지 않고 **`tools/views/links.mjs`가 DB + 기록 + `annotations/links.json`을 합쳐 계산한다** → 시안 `data/views/links/`,
조회 `node tools/query.mjs links <씬|단위>`(아래 "관계선"). 기록 · 수동 엣지는 빌드 입력이 아니라서(고칠 때마다 DB를 다시 만들지 않게 — X1 작중 연대기와 같은 방식) 질의 때 계산한다(약 1.5초).

| 칼럼 | 설명 |
|---|---|
| `from_id`, `to_id` | `stories.id` |
| `type` | 아래 "엣지 타입" — `prereq` / `sequel` / `setup_payoff` / `callback` / `reversal` / `character` / `keyword` |
| `strength` | 1~3. 게임 확정 조건은 3, 시트 엣지는 시트의 ◆ 개수 |
| `origin` | `game-condition` / `auto` / `record` / `manual` / `sheet`. `sheet`는 시트의 추천 선행 — **참고용, 분석 입력 아님** |
| `note` | 근거 메모 |

`query.mjs links`는 `--sheet`를 줄 때만 `origin='sheet'` 엣지를 보여 준다.

#### 엣지 타입 — 한 목록 (B0a, 2026-10-04 · T3-4)

스토리(씬 · 단위) 사이의 관계만 엣지다. 기본은 **씬 → 씬**이고, 단위 → 단위는 그것을 (from 단위, to 단위, 타입)마다 센 것이다
(같은 단위 안 엣지는 단위 그래프에서 뺀다). 방향은 읽는 순서(출시순 한 줄)다 — 대칭인 `character` · `keyword`도 앞에서 뒤로 둔다.

| 타입 | 뜻 | 어디서 나오나 | origin | 지금 |
|---|---|---|---|---:|
| `prereq` | 게임이 A를 먼저 보게 한다 | 호감도 스토리 `condition_scenario_group_id` · 빠진 조건은 번호 순 추정 — 모두 한 인물(단위) 안 | `game-condition` · `auto` | 756 · 16 (DB) |
| `sequel` | 바로 이어지는 이야기 — 다음 챕터 · 같은 이벤트 시리즈의 다음 편 · 이벤트 → 그 이벤트 유실물 · 서브퀘스트 다음 편. 같은 단위 안 다음 씬은 순서로 알므로 엣지로 두지 않는다 | 키 · 게임 순서에서 자동(X2 — 메인 번호 순 · `sub:<이름>_NN` · 유실물 `-전` → `-후` · 이벤트 유실물), 이벤트 · 사이드 연작은 수동(Claude 확정) | `auto` · `manual` | 100 · 28 |
| `setup_payoff` | 떡밥 → 회수: 의문을 던진 씬(2회독: 복선을 흘린 씬) → 드러내 놓고 푼 씬 | 1회독 의문 회수 `Q<n>-k`(from = `Q<n>`의 첫 근거 씬, to = 회수의 첫 근거 씬) · 2회독 암시 `E<n>` | `record` | 1,272 (1회독 294 · 2회독 978) |
| `callback` | 앞서 드러난 사실을 다시 드러냄 · 재언급 | 1회독 사실 드러냄 `F<n>-k` · 2회독 재언급 `E<n>`(B1a) | `record` | 833 (97 · 736) |
| `reversal` | 앞서 드러난 사실이 뒤집힘 | 1회독 사실 뒤집음 `F<n>-k` | `record` | 8 |
| `character` | 같은 인물이 중심으로 나온다 | 대상 공유 사슬(X2 — 아래 "관계선"). 애장품 소유(호감도 스토리 1편 → 애장품)는 게임 데이터 | `auto` · `game-condition` | 1,615 · 21 |
| `keyword` | 같은 비인물 대상(장소 · 조직 · 개념 · 사건 · 물건)을 다룬다 | 대상 공유 사슬(X2) | `auto` | 1,608 |

- `origin = record` — 확정 · 후보 기록(1회독 `annotations/read1/`, 2회독 `annotations/read2/`)에서 뽑은 엣지. 기록 ID(`Q12-2` · `E51`) · 상태 · 확신도를 함께 둔다 —
  확정 전 후보로 만든 엣지는 `status = 후보`로 남고 관계선 보고서 · 조회가 따로 센다 · 표시한다(X2). DB에는 싣지 않는다(위).
- 2회독 기록도 이 타입으로 뽑는다(B1a — docs/annotations.md "2회독 기록" › 떡밥): 떡밥 `E<n>`의 암시 → 가리킨 사실 · 사건의 첫 씬, 의문이면 회수마다 `setup_payoff`,
  재언급은 가리킨 기록의 첫 씬 → 재언급 씬 `callback`. 줄기 `J<n>`만 가리키면 씬 엣지가 없다. 뽑는 함수는 tools/records/read2.mjs `read2Edges`(1회독 사건 엣지와 같은 모양 + `record` · `point` · `act`).
  수동 엣지 파일(T4-3)도 같은 타입을 쓴다 — 아래 "수동 엣지".
- 없앤 것: `same_arc`(같은 사건 · 편) — 편 묶음은 `sequel`, 같은 수수께끼는 떡밥 줄기(B0b) 소속으로 노드 속성이다.
  `contradiction`(설정 충돌) — 설정 오류 추정(`slips`)은 일부러 모으지 않는 메모라(CLAUDE.md) 엣지로 올리면 빠짐없는 목록처럼 보인다.
  단위 메모로 두고 씬 리더(T5-5)에 보인다. 이야기 안의 뜻 있는 모순(거짓말 · 착각)은 이미 뒤집음 → `reversal`이다.
- 엣지가 아닌 관계: 기록끼리(회수의 답 `answer` · 뒤집음의 `replacedBy`)는 떡밥 흐름 화면의 선이고, 떡밥 줄기끼리의 관계는 `annotations/threads.json` `relations`(B0b-1, docs/annotations.md "떡밥 줄기")다.
  작중 시점 기준(`times`의 `ref`)은 작중 연대기(X1)의 입력이다. 화면별 쓰임은 [views.md](views.md).

#### 수동 엣지 — `annotations/links.json` (T4-3 · T4-4, B1a)

기록(1회독 사건 · 2회독 떡밥)이나 게임 데이터에서 나오지 않는 스토리 사이 관계를 사람 판단으로 더하거나, 자동 엣지를 지운다. 해석이라 후보 → Claude 확정, 사용자가 뒤집는다.
JSON 하나(T4-1: 기계가 읽는 표는 JSON). 필요해질 때 만든다 — 예시는 `tests/fixtures/read1/_links.json`. 검증 · 리뷰는 기록 도구(`records.mjs check` · `review 엣지` · `set Y1 확정`).

```json
{ "session": "M03", "by": "claude", "date": "2026-10-04",
  "edges": [
    { "id": "Y1", "type": "sequel", "from": "sub:로망티스트_00", "to": "sub:로망티스트_01", "strength": 3, "records": ["Q1-2"],
      "reason": "같은 서브퀘스트의 다음 편", "confidence": "확실", "status": "후보" },
    { "id": "Y2", "type": "character", "from": "d_ex_elevator_01", "to": "sub:로망티스트_00", "drop": true,
      "reason": "인물만 겹치고 서로를 딛지 않는다 — 자동 엣지를 지운다", "confidence": "추정", "status": "후보" } ] }
```

| 칸 | 필수 | 뜻 |
|---|---|---|
| `id` | ✓ | `Y<n>` — 한 번 붙이면 바꾸지 않는다 |
| `type` | ✓ | 위 "엣지 타입" 일곱 가지 |
| `from` · `to` | ✓ | 씬 ID 또는 읽기 단위 키(read.mjs 키). 둘은 같은 단계로(씬끼리 · 단위끼리 — 병합이 같은 끝점끼리 비교한다). 방향은 읽는 순서 |
| `strength` | | 1~3 |
| `drop` | | `true`면 같은 (from, to, type)의 자동 엣지를 지운다 |
| `records` · `evidence` | | 근거 — 기록 ID 배열(`Q1-2` · `F12` · `J3`) · 씬 줄(`[{scene, lines}]`) |
| `reason` · `confidence` · `status` · `by` · `note` · `reviews` | | 후보 공통 칸 |

**병합 규칙(T4-4)** — `tools/records/read2.mjs` `mergeEdges(auto, manual)`. 같은 엣지 = (from, to, type)이 같은 것.
- 수동만 있으면 `origin = manual`로 더한다. 둘 다 있으면 **수동이 이긴다** — 수동 값(strength · note)을 쓰고, 자동 엣지는 `auto`에 그대로 **보존**한다.
- 수동 `drop`은 자동 엣지를 지운다 — 지운 자동 엣지는 `dropped`에 `dropped_by`(Y ID)와 함께 남는다(보존). 지울 자동 엣지가 없으면 `unmatched`(알림).
- 기각된 수동 엣지는 없는 것으로 친다. 후보는 합치되 상태를 남긴다(확정값처럼 쓰지 않는다).
- 같은 키의 자동 엣지가 여럿일 수 있다(다른 기록 · 대상이 같은 씬 쌍을 잇는다) — 모두 따로 두고, 수동은 걸린 것을 모두 이기거나(`auto` 배열) 지운다(X2).
- **끝점이 단위 키면 단위 쌍(`from_unit` · `to_unit`)으로 견준다**(X2) — 단위 사이 관계를 한 번에 더하거나 지운다. 더한 엣지의 씬 끝점은 앞 단위의 마지막 씬 → 뒤 단위의 첫 씬.
- 수동 엣지 파일은 DB에 싣지 않는다(X2) — 관계선(`tools/views/links.mjs`)이 읽는다(`ensure-db.mjs` 지문에서도 뺀다). `records`에는 사실 · 의문 · 사건 · 줄기 · 시점(`S<n>`) ID를 쓴다.
  검증기는 단위끼리 이은 수동 엣지가 읽는 순서를 거스르면 경고한다.

#### 관계선 — `tools/views/links.mjs` (X2, T3-5)

스토리 사이 엣지를 한 목록으로 모은다. 모두 씬 → 씬, 방향은 읽는 순서(출시순 한 줄). 단위 → 단위는 (from 단위, to 단위, 타입)마다 센 것(같은 단위 안은 뺀다 — 호감도 스토리 조건은 모두 한 인물 안).
시안 `data/views/links/` — `scene-edges.csv`(엣지 하나에 한 줄) · `unit-edges.csv`(단위 쌍 · 타입마다 수 · 세기 · origin · 후보 수 · 기록 ID · 대상) · `units.csv`(단위별 이웃 수 · 고립 · 중심 대상) ·
`centers.csv`(단위 × 중심 대상 — 기록 수 · 말한 줄 · 몫 · 이름 줄 · 그 대상이 중심인 단위 수 · 까닭) · `dropped.csv`(수동 drop으로 지운 자동 엣지) · `report.md`.
조회 `node tools/query.mjs links <단위|씬> [--type character,keyword] [--min 2] [--sheet]`.

| 출처 | 타입 · origin | 규칙 |
|---|---|---|
| 게임 | `prereq` · `character` — `game-condition` · `auto` | DB `edges`(빌드) 그대로. 시트(`sheet`)는 싣지 않는다 |
| 키 · 게임 순서 | `sequel` — `auto` | 메인 다음 챕터(번호 순, 43 · 44 병행도 번호 순) · `sub:<이름>_NN` → NN+1 · 유실물 `…-전` → `…-후` · 이벤트 → 그 이벤트 유실물(`ERELIC_EVENT`) |
| 기록 | `setup_payoff` · `callback` · `reversal` — `record` | 1회독 사건(`read1Edges`) · 2회독 떡밥(`read2Edges`). 기각은 빼고 후보는 상태를 남긴다 |
| 대상 공유 | `character`(인물) · `keyword`(비인물) — `auto` | 대상이 단위의 **중심**이면 그 대상이 중심인 바로 앞 단위(읽는 순서)와 잇는다 — 대상마다 사슬(중심 단위 수 − 1). 지휘관은 뺀다. 끝점 = 앞 단위에서 대상이 마지막으로 나온 씬 → 뒤 단위에서 처음 나온 씬(`from_line` · `to_line`) |
| 수동 | 아무 타입 — `manual` | `annotations/links.json`(`Y<n>`, Claude 확정) — 위 병합 규칙 |

- **중심**(Claude, X2): 단위 U에서 대상 T가 중심이다 = ① U의 기록 2건 이상이 T를 다룬다(1회독 사실 · 의문의 `about`, 2회독 떡밥 · 생활상의 `about`, 인물 변화의 `person`) 또는
  ② 인물이면 U에서 이름표로 5줄 이상 · U의 말한 줄(지휘관 빼고)의 10% 이상을 말한다(2회독 암시 언급 `speaker`도 말한 줄) 또는 ③ 비인물이면 이름(`named` · `alias`)이 5줄 이상 나온다.
  까닭은 `centers.csv` `why`(기록 · 말함 · 이름). 이름만 한 번 불린 인물 · 지나가는 언급은 중심이 아니다 — 그래서 사슬이 "그 인물 · 대상을 다룬 바로 앞 이야기"를 가리킨다.
  왜 사슬인가: 모든 쌍을 이으면 라피 하나로 수천 선이 생긴다. 사슬은 대상마다 선이 (단위 수 − 1)이고, 인물로 거르면 그 인물이 중심인 단위를 출시순으로 잇는 궤적이 된다(화면 2 · 5).
- **세기**(1–3, "앞 단위를 먼저 볼 만한 정도"): 3 게임 조건 · 다음 편(자동 · 수동 3) · 확실한 기록 / 2 추정 기록 · 사이가 떨어진 연작(수동 2) · 대상 공유 / 1 흔한 대상 공유.
  **흔한 대상** = 중심인 단위가 읽기 단위의 10%(481 → 48)를 넘는 대상 — 니케 · 방주 · 랩쳐 · 지상 · 아니스 · 라피 · 중앙 정부 · 네온(note `흔한 대상`). 화면 기본값에서 숨기기 좋다(docs/views.md 화면 공통 "어디에나 걸리는 대상").
- 기록 엣지가 읽는 순서를 거스르면(정의보다 앞선 사건) 1회독 · 2회독 도구와 같이 문제로 보고한다. 자동 · 수동 엣지가 거스르면 보고서 "문제"에 오른다.

| `name` | 덩어리에 나온 이름표 · 이름(여럿이면 ` · `) |
| `speaker` | 그 줄을 말한 사람이 이 대상인가 — speaks = 1 |
| `origin` · `confidence` · `status` | 자동은 `auto` · `확실` · `확정` |

`scene_targets`(씬별 대상 인덱스): 씬 × 대상마다 `speaks` · `named` · `alias` 줄 수 · `first_seq`. 조회는
`node tools/query.mjs appear <대상>`(나온 단위 · 씬을 출시순으로, 처음 · 마지막 등장 — `--scenes` · `--how` · `--from` · `--to`) ·
`targets <씬|단위>`(그 자리의 대상, ★ = 처음 등장). 시안 `node tools/views/mentions.mjs` → `data/views/mentions/`(targets · units · report).

**speaks** — 범위 안 줄의 이름표 풀이(`lines.speaker_target`, "이름표 분류")를 그대로 쓴다. 여럿 이름표는 그 대상들 모두, 지휘관은 이름표 없는 Self · MessengerSelf 창.
미상 이름표(`???` 829 · 그 밖 134줄)는 누구에게도 잇지 않는다 — `???`는 매번 다른 사람이라 정체는 2회독 암시 언급(`speaker: true`)이 씬 · 줄마다 적는다.
진행률은 `node tools/records.mjs progress --read2`(미상 이름표 줄 정체 적음 n/963).

**named · alias — 검색 규칙**:

- 비인물 이름은 사전 건수와 같은 규칙("비인물 사전" `compileNames` — 낱말 앞, `except`). 합성어(`방주민`)도 언급으로 친다.
- 인물 이름은 더 좁힌다(`compilePersonNames`): 낱말 앞에서 시작하고 **이름 뒤 낱말 나머지가 비었거나 꼬리**(`PERSON_TAIL` — 호칭 접미 `님 · 씨 · 언니 · 들 · 답다`,
  조사 `이 · 가 · 에게 · 한테도 …`, 서술격 `였어 · 이라면 · 잖아 …`)여야 한다 — `진짜` · `신경` · `나가다`의 활용 일부를 뺀다(실측: 3글자 이상 이름의 97.5%가 꼬리 규칙을 지난다).
  한 자리에 여러 이름이 걸리면 가장 긴 것(`그레이브` ⊃ `그레이`), 더 긴 비인물 이름 안의 인물 이름(`엘리시온 하퍼`)은 뺀다.
- 두 인물이 나누는 이름(`사쿠라` — TETRA · 콜라보)은 그 단위에서 이름표로 말하는 쪽 하나에 건다. 둘 다 · 아무도 아니면 뺀다.
- 창 Action · Route · Input은 보지 않는다.
- 인물 이름의 `target_names.lines_in_scope`는 이 규칙으로 걸린 줄(쓰는 법과 상관없이), 인물 `targets.lines_in_scope` · `stories_in_scope`는 자동 줄에 쓴 이름의 줄 · 씬이다.

**표본 정밀도 — `annotations/dictionary/mention-precision.json`** (빌드 입력):

이름(대상 · 이름 쌍)마다 자동으로 걸린 줄의 결정적 표본(`node tools/query.mjs sample <이름> --n N --seed S`, `--tsv`로 판정 표)을 떠 그 대상이 맞는지 판정한다.
한 줄 = `{ target, name, sample, correct, auto, unit?, except?, seed?, note, by, date }`. `?`(문맥으로 모름)는 틀림으로 센다.

| `auto` | 쓰는 법 | 기준 (`PRECISION_FLOOR` 80%, 테스트가 본다) |
|---|---|---|
| `all` | 어디서나 | correct / sample ≥ 0.8 |
| `unit` | 그 인물이 이름표로 말하는 단위 안에서만 — 흔한 낱말과 겹치지만 자기 단위에서는 맞는 이름(`나가` · `파워` · `신`) | 밑이고, `unit`(`--in-unit` 표본)이 ≥ 0.8 |
| `off` | 자동에서 뺀다(건수는 센다) — DB `target_names.mention_mode`에 남아 화면에 "자동에서 뺌"으로 보인다 | 그 밖 |

- `except`(인물만): 그 자리를 덮는 더 긴 표기를 뺀다 — `볼트` ↔ `볼트 주니어`(다른 로봇). 비인물은 사전 파일의 `except`.
- 표본 크기: 한 글자 · 로마자 · 흔한 말 · 꼬리 빗나감 · 비인물 오탐 주의 10줄, 그 밖에 위험(두 글자 · 단위에서 안 말함) 5줄, 나머지 3줄.
  재는 범위: 걸린 줄이 있는 인물 이름 전부(새 인물 이름이 생기면 테스트가 재라고 한다) + 비인물 `caution` 이름.
- 2026-10-05(B2): 392이름 · 표본 2,185줄 · 맞음 92%, `all` 364(그 이름만 98%) · `unit` 17 · `off` 11(`진` · `마리` · `버디` · `쉘터` · `프로토콜` …).
  판정은 Claude(표본 판정을 서브에이전트 넷에 나눠 맡기고, 기준 밑은 Claude가 `--in-unit`으로 다시 봄). 사용자가 뒤집으면 `by`를 사용자로 고친다.
- `DB target_names.precision` = `맞음/표본`(+ ` · 단위 맞음/표본`). 보고서 `data/views/mentions/report.md` "표본 정밀도".

**자동 줄과 기록 줄 합치기** (X3이 한다): 자동 줄과 2회독 암시 언급 줄은 둘 다 둔다(기록 줄은 기록 ID · 상태를 가진다). 등장을 셀 때는
(씬, 대상)마다 줄의 합집합으로 세고, 암시 언급 `speaker: true` 줄은 그 대상이 말한 줄로 센다. 후보는 확정값처럼 쓰지 않는다.

| `kind` | 갈래(자유 낱말): 도시 · 지역 · 시설 · 탈것 / 정부 · 기업 · 스쿼드 · 단체 / 존재 · 랩쳐 등급 · 랩쳐 종류 · 기술 / 전쟁 · 작전 / 장치 · 무기 … |
| `names` | 다른 이름 `[{name, how, caution?, except?}]` — how: `정식 명칭` · `약칭` · `별칭` · `표기` · `영문` · `이명` |
| `caution` · `except` | 표준명의 오탐 주의 사유 · 검색에서 뺄 더 긴 표기. `names` 칸 안에 두면 그 이름에만 붙는다 |
| `note` · `evidence` | 메모 · 무엇인지 보여 주는 줄 `[{scene, lines}]`(lines는 `lines.seq`) — 테스트가 그 줄이 있고 이름이 들었는지 본다 |
| `wrong` | 재 보니 0건(또는 거의 없음)이라 넣지 않은 추측 표기 — 테스트가 이름에 없고 대상 건수의 5%를 넘지 않는지 본다 |

**검색 규칙** (`compileNames`) — 건수와 앞으로의 자동 기록(T3-9 `named` · `alias`, B2)이 같은 규칙을 쓴다:

- 이름을 글자 그대로(대소문자 구분) 찾되 **낱말 앞에서 시작하는 곳만** — 바로 앞 글자가 한글 · 로마자 · 숫자가 아니어야 한다.
  뒤는 조사가 붙으므로 따지지 않는다. FTS 접두 검색 `"이름"*`과 같은 뜻이다.
- 여러 낱말 이름의 띄어쓰기 자리는 한글 · 로마자 · 숫자가 아닌 글자 여럿과도 맞는다(`아우터… 림` · `[아크 가디언] 작전` · `세븐스, 드워프`) — FTS 구 검색과 같다.
  테스트가 규칙(`except`) 없는 한글 이름 109개의 건수가 FTS와 똑같은지 본다.
- 로마자 · 숫자로 끝나는 이름은 뒤 글자도 로마자 · 숫자가 아니어야 한다(`Ark` ≠ `Arkham`).
- `except`: 그 자리를 덮는 더 긴 표기가 있으면 뺀다 — `테트라` ↔ `테트라포드`, `엘리시온` ↔ `엘리시온 하퍼`(메신저 대화명 = 인물).
- 한 이름이 다른 대상의 이름을 품으면 둘 다 센다(`지상 탈환` 줄은 `place:지상`에도, `갓데스 폴` 줄은 `org:갓데스`에도 걸린다).
  대상 건수는 그 대상 이름들이 걸린 줄의 합집합이다. 한 표기가 두 대상에 걸리는 것은 막는다(빌드 ⚠ · 테스트).
- 건수는 **범위 안**(`stories.in_scope = 1`) 대사 줄 수 · 씬 수다. 인물 대상은 꼬리 규칙을 더한 언급 DB 규칙으로 센다(위 "언급 DB", B2).

**넣는 기준** (v1):

- 원문에 그 이름 그대로 나오는 고유 이름(장소 · 조직 · 사건 · 물건)과 세계관 용어(랩쳐 · NIMPH · 침식 · 크레디트)를 넣는다.
  흔한 일반 명사(코어 · 쉘터 · 엘리베이터 · 사관학교 · 메이드 카페 · 보호소 · 여왕 · 여신 · 이단 · 구시대)는 뺐다 — Q-A2-4.
- 무엇이 무엇을 가리키는지 해석이 필요한 것은 별칭으로 넣지 않는다 — `E.H.`(엔터 헤븐을 만든 인물, fl:enter_heaven_01#11)는 조직의 약칭이 아니다.
  같은 대상인지 덜 확실한 별칭(`감찰 부대` → 오버시어 등)은 `caution`을 달고 docs/open-questions.md(Q-A2-3)에 올렸다.
- 이름 있는 한 개체(랩쳐의 퀸)는 인물(`person:퀸`, people.json), 여러 개체가 있는 랩쳐 종류(프레데터 등)는 `concept:` — Q-A2-2.
  탈것(배 · 비행선)은 무대가 되므로 `place:` — Q-A2-1.
- 게임 데이터에서 본 것: 챕터 제목은 흔한 낱말(추락 · 침식 · 인식 …)이라 대상이 아니다. 이벤트 제목은 영어라 한글 음역을 쟀다 —
  에덴(EDEN SPEAR) · 엔터 헤븐 · 아크 가디언 · 빌런 연합 · 오버 더 호라이즌 · 블루워터 아일랜드 · 코인 러시는 있고
  네버랜드 · 오버 존 · 레드 애쉬 · 라스트 킹덤은 0건. 애장품 33개는 이름이 원문에 거의 없다(낡은 나침반 · 형사 수첩 · 인장 반지 0건) —
  애장품 스토리는 `fav:` 노드로 이미 있다. 유실물 제목에서 방주 추첨권 · 하모니 큐브 · 궤도 엘리베이터 · 데일리 아크를 얻었다.
- 오탐 주의(`caution`) 15개: 흔한 말과 겹침(지상 · 침식 · 프로토콜 · 베스트셀러 · 양산형 · 정부 · 추첨권 · 미미르)이나
  다른 것과 섞임(리와인드 · 인큐베이터 · 감찰 부대 · 아크 가디언 · 랩쳐의 침공 · 미사일스). 자동 기록(B2)은 이 이름들의 표본 정밀도를 재 기준 밑은 뺐다(위 "언급 DB").
- 새 대상 · 표기는 1회독 · 2회독이 더한다. `node tools/query.mjs search <표기>`로 재고 넣는다 — 0건이면 빌드가 ⚠를 띄우고 테스트가 실패한다.
  빠진 것으로 알고 있는 것: 이름 있는 랩쳐 개체 · 종류 대부분(마더 웨일 등, Q-A2-2), 인물 쪽 별칭 · 이명, 작은 가게 · 시설.

## 시트 `추천 선행 스토리` 문법

시트 자체가 범례를 담고 있다 (메인 CHAPTER.08~11행의 해당 칼럼):

| 표기 | 시트의 정의 | `strength` |
|---|---|---|
| `◆◆◆` | 무조건 선행으로 봐야 함 | 3 |
| `◆◆` | 선행으로 봐야 이해하기 좋음 | 2 |
| `◆` | 선행으로 보면 좋지만 굳이 안 봐도 됨 | 1 |
| `X` | 선행으로 볼 것 없으니 그냥 봐도 됨 | — (엣지 없음) |
| `?` | 아직 안 봐서 모름 | — (미검토 표시) |

값의 형태:

```
◆◆◆ ARK GUARDIAN ◆◆ CHAPTER.42 유일 / FOOTSTEP, WALK, RUN ◆ COIN IN RUSH / CHAPTER.44 행보
```

- `◆` 묶음이 등급을 열고, 그 뒤 항목들이 그 등급에 속한다
- `/`와 `또는`이 같은 등급 내 항목을 나눈다
- 항목은 스토리 제목 또는 캐릭터 이름이다

### 파싱 시 반드시 걸러야 하는 것

**시트 상단 13행(메인 CHAPTER.00~12)의 이 칼럼에는 범례와 안내문이 들어 있다.**
그대로 파싱하면 `무조건 선행으로 봐야 함`이라는 이름의 스토리가 생긴다.
`tools/normalize/legend.json`의 문장 목록으로 제외한다.

해석되지 않는 항목은 **엣지로 만들지 않고 `sheet_rows.unresolved`에 남긴다.**
조용히 버리면 관계가 사라진 것을 알 수 없다.

## 한국어 전문 검색 — 두 갈래로 간다

한국어는 조사가 붙어 `랩쳐가`, `랩쳐를`이 한 토큰이 된다.
FTS5 `unicode61`은 공백 단위로 토큰을 만들므로 **`MATCH '랩쳐'`는 대부분을 놓친다.**

실측 (287,882줄 기준, `LIKE '%...%'`를 정답으로 봤을 때):

| 키워드 | LIKE | `MATCH "kw"` | `MATCH "kw"*` | trigram |
|---|---:|---:|---:|---:|
| 랩쳐 | 2,154 | 415 | **2,152** | 0 |
| 방주 | 3,033 | 739 | **3,033** | 0 |
| 니힐리스타 | 201 | 38 | **201** | **201** |
| 엘리시온 | 172 | 72 | **172** | **172** |
| 중앙 정부 | 396 | 116 | **396** | **396** |

결론:

- **기본은 접두 검색 `MATCH '"키워드"*'`** — 글자 수 제약이 없고 LIKE와 사실상 일치한다.
- **`lines_tri`(trigram)는 3글자 이상에서만 유효**하다. 2글자 질의는 0건이 나온다.
  대신 단어 중간 매칭(`대랩쳐`)까지 잡는다 — 접두 검색이 놓친 랩쳐 2건이 그것이다.
- `tools/query.mjs`가 이 규칙을 자동으로 적용한다.

## 시트 ↔ 데이터 연결 (참고용)

시트는 참고자료라 비교용으로 이어만 둔다. 시트와 데이터가 다르면 데이터를 따른다.
`annotations/aliases.json`이 표기 차이를 흡수한다. 현재 상태:

| 시트 유형 | 행 | 연결 |
|---|---:|---|
| 메인 | 49 | ✅ 49/49 — `CHAPTER.NN 이름` → 챕터 번호 |
| 에피소드(= 호감도 스토리) | 193 | ✅ 193/193 — `resource_id` 기준 |
| 이벤트·퀘스트 | 92 | ✅ 아카이브O 60/60. 아카이브X 32 중 30은 시트에만 있고, 2는 데이터에 있다 |
| 사이드 | 5 | 시트에만 있다 |
| 애장품 | 21 | ✅ 21/21 — 아이템 ID + 소유 캐릭터. 시트 표기 `애착 베게`(데이터 `애착 베개`)는 별칭(`favorites`) |

제목 비교 키(build.mjs `nk()`)는 대소문자·공백·문장부호를 무시하고 글자·숫자·`_`만 남긴다.
`D.ARK HERO` → `darkhero`, `CLAY, MORE!` → `claymore`. `_`를 남기는 건 아카이브 접두(`event_…`)도
같은 키로 비교하기 때문이다 — 지우면 접두 매칭이 통째로 깨진다(실측: 연결 313 → 266).

데이터에 있을 법한 행(메인·에피소드·애장품·아카이브O)이 `sheet:` 노드로 떨어지면 build.mjs가
출력에 목록을 띄운다. 참고용 연결이라 경고는 아니다. 표기 차이면 `aliases.json`에 별칭을 더하면 된다.
