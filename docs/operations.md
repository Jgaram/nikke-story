# 운용 — 세션을 어떻게 돌리나

CLAUDE.md에서 가리키는 자세한 운용 문서다. 무엇을 할지는 [SESSIONS.md](../SESSIONS.md)(남은 일)와 사용자의 지시가 정하고, 이 문서는 **어떻게 돌리는지**를 적는다.
옛 판(1회독 · 2회독 · 분석을 순서대로 돌리던 때의 관리자 배정 · effort 표)은 [history/operations.md](history/operations.md).

## 방식 셋

| 방식 | 언제 | 사용자가 하는 말 |
|---|---|---|
| **지시 세션** (지금 주로) | 사이트 피드백 · 고치기 · 다시 읽기 · 질문 — 한 세션에 끝나는 일 | 하고 싶은 일을 그대로 |
| **"다음 일"** | SESSIONS.md "할 일"에 줄 세운 일 | "다음 일" |
| **관리자** | 여러 세션 · 에이전트로 큰 묶음을 돌릴 때 — 순차 또는 병렬 | "W9를 에이전트로 병렬로 — 한 번에 5개씩" 등 |

## 지시 세션

1. **읽을 것은 CLAUDE.md와 시킨 일에 걸린 문서뿐이다.** SESSIONS.md · docs/history/는 필요할 때만 `grep -n`으로 연다.
2. **어디부터 보나**
   | 시킨 일 | 먼저 볼 곳 |
   |---|---|
   | 사이트 화면 · 동작 | docs/views.md "파일 배치 · 모듈 규약 · 실행법 (W1)"과 그 탭의 절 → `site/tabs/<탭>.js` · `tools/site/export/<탭>.mjs` |
   | 화면에 뜬 기록 내용(사실 · 의문 · 줄기 · 변화 …)이 틀림 | `node tools/records.mjs find <낱말>` · `review <단위>` → docs/annotations.md 그 기록의 절 |
   | 중요도 등급 · 선행 | docs/importance.md(판정 카드)만. 외부 참고 표는 열지 않는다(CLAUDE.md) |
   | 줄거리(공개 개요) | docs/annotations.md "공개 개요" · `node tools/synopsis.mjs` |
   | 분류 이유 · 연대기 추정 이유 문장 | docs/annotations.md "팬용 문장" · `node tools/blurbs.mjs` |
   | 작중 연대기 | docs/annotations.md "작중 연대기" · `node tools/query.mjs chrono <단위>` |
   | 원문을 다시 읽어야 함 | [docs/tools.md](tools.md) "원문 읽기" — 필요한 씬만 |
3. **해석 기록을 고칠 때** — 사용자가 말한 판단은 `--by 사용자`로 남긴다(Claude가 다시 바꾸지 않는다). Claude가 다시 읽고 고친 것은 `--by claude`와 근거.
4. **고친 뒤 다시 뽑기** — 기록을 고쳤으면: `node tools/records.mjs check` → `node tools/views/draft.mjs`(data/views — 연대기 · 공개 축도 같이) →
   `node tools/site/export.mjs`(바뀐 탭만이면 `--only <탭>`) → `node tools/check-quotes.mjs` → `node --test tests/*.test.mjs` → 커밋 · push.
   사이트 코드만 고쳤으면 내보내기는 건너뛴다. 화면 확인은 `node tools/site/serve.mjs` + 헤드리스 크로미움(docs/views.md "실행법").
5. **한 세션을 넘는 일**(여러 단위 다시 읽기 · 큰 재설계)은 그 자리에서 다 하지 않는다 — SESSIONS.md "할 일" 끝에 항목으로 넣고 사용자에게 알린다.
6. **기록** — 끝나면 [docs/feedback.md](feedback.md)에 한 묶음 덧붙인다. 규칙 · 결정이 바뀌었으면 **주제 문서를 먼저 고치고** 피드백 기록에는 "→ 어디 반영"만 적는다.

## "다음 일"

SESSIONS.md "쓰는 법"대로 한다 — 첫 미완료 항목 하나, 중간 저장, 완료 표시와 인계, 다음 항목 알림.

## 동시에 여러 세션

지시 세션과 관리자 세션처럼 둘 이상이 같이 돌 수 있다. 세션마다 컨테이너가 따로라 DB는 서로 상관없다.

- push가 거절되면 `git pull --rebase origin main` 뒤 다시 push한다(CLAUDE.md "브랜치 규칙").
- **생성 파일**(`site/data/` · `data/views/` · `data/release/`)에서 충돌이 나면 손으로 합치지 않는다 — `git checkout origin/main -- <파일>`로 받아 온 뒤
  생성기(위 "다시 뽑기")를 다시 돌려 `git add`하고 `git rebase --continue`. `site/data/manifest.json`은 내보낼 때마다 시각이 바뀌어 늘 충돌한다.
- 같은 손 문서를 둘이 고치는 일은 피한다 — SESSIONS.md는 자기 항목만, docs/feedback.md는 끝에 덧붙이기만 한다.
- 같은 기록 파일(`annotations/…`)을 두 세션이 동시에 고치게 되면 나중 세션이 상대 커밋을 받아 다시 확인한 뒤 고친다.

## 컨텍스트 예산

사용자는 세션 컨텍스트가 많이 차는 걸 싫어한다. 자동 요약이 날 일이 없게 여유를 크게 둔다(Opus 5.5 컨텍스트 1M, 한국어 1자 ≈ 1토큰).

- **긴 문서는 통째로 읽지 않는다** — docs/annotations.md(8만 자) · docs/views.md(6만 자) · docs/schema.md(3만 자) · docs/history/(50만 자)는 `grep -n`으로 절을 찾아 그 부분만.
- **원문** — 지시 세션의 다시 읽기는 필요한 씬만, 합쳐 5만 자 안쪽. 넘으면 SESSIONS.md에 항목으로 올린다.
  읽기 세션(신작 N3 등)은 원문 10만 자 이하 + 되짚어 읽기 5만 자 이하, 멈춤 15만 자(자세히 history/reading.md "컨텍스트 예산 (읽기 세션 때)").
- **큰 출력은 파일로**(scratchpad) 보내고 필요한 부분만 본다. `query.mjs sql`은 100행까지만 찍는다.
- **세션 수는 따지지 않는다** — 세션을 여는 건 사용자 몫이다. 세션을 줄이려고 한 세션의 분량을 늘리지 않는다.
- 그래도 자동 요약이 나면 저장한 단위는 두고 하던 단위는 새 세션에서 다시 한다. 요약된 기억으로 근거 줄을 쓰지 않는다.

## 코드 · 설계 작업

- CLAUDE.md "코드 규약"을 따른다. 정한 형식 · 스키마는 docs/schema.md · docs/annotations.md에 적는다 — 다음 세션은 문서를 보고 쓴다.
- 끝내기 전에 `node --test tests/*.test.mjs`(DB가 필요하다 — 아래 "원본 레포")와 검증기가 통과해야 한다.
- 화면에 뜰 문장 · 표시의 시안을 사용자에게 보일 때는 표로만 주지 말고 **지금 화면과 시안을 나란히 찍어** 보인다(데이터를 고친 사이트 사본을 scratchpad에 두고 헤드리스 크로미움으로 — 사용자, 2026-10-10 W14a).

## 관리자

관리자는 **작업 세션 · 에이전트의 작업 과정을 읽지 않는다** — 상태(SESSIONS.md) · git 커밋 · 진행률 · 보고만 본다(관리자 컨텍스트를 아낀다).
👤 항목에 닿거나 · 같은 일이 두 번 실패하거나 · 관리자 컨텍스트가 25%쯤이면 어디까지 했는지 짧게 알리고 멈춘다. 다음 관리자는 SESSIONS.md만 보고 잇는다.

### 관리자 — 병렬 (한 세션에서 에이전트로)

**묶음끼리 인계가 없고 쓰는 파일이 안 겹칠 때**(예: W9 공개 개요) 쓴다. 구체 지시문은 그 항목(SESSIONS.md W9 공통)에 둔다.

1. **준비** — 원본 레포를 붙이고 DB를 **에이전트를 띄우기 전에** 한 번 만든다(여럿이 동시에 오래된 DB를 보면 같이 다시 만들다 깨진다).
2. **물결** — 한 번에 4–6개, 묶음 하나에 에이전트 하나. 에이전트는 자기 묶음의 파일만 쓰고 git · SESSIONS.md · 생성 파일 · DB는 건드리지 않는다. 사용자에게 묻지 않는다.
3. **에이전트 하나가 끝날 때마다** — 관리자가 진행률 · 검증기로 확인 → 내보내기 → 커밋 · push → 항목 `[x]`와 인계 한 줄. 남은 단위가 있으면 `[~]`로 두고 새 에이전트.
4. **물결이 끝나면** — 묶음마다 결과 2–3개를 표본으로 보고, 어긋난 것이 있으면 지시문에 한 줄 더해 다음 물결에 준다.

### 관리자 — 순차 (작업 세션을 하나씩)

**앞 세션의 결과가 다음 세션의 입력일 때** 쓴다(옛 1회독 · 2회독처럼). 한 번에 하나씩, SESSIONS.md 순서대로.

1. **다음 항목** — `git pull origin main` 뒤 SESSIONS.md의 첫 `[ ]` · `[~]`. 맡은 범위 밖이거나 👤면 멈추고 알린다.
2. **작업 세션 열기** — 같은 환경 · 레포 · 모델로 새 세션을 열고 맡긴다:
   ```
   다음 일. (관리자 세션이 연 세션이다 — 사용자가 지켜보지 않는다. 사용자에게 물을 것이 생기면
   docs/open-questions.md에 적고 잠정값으로 진행하고, 잠정값으로 못 가면 진행 메모를 남기고 [~]로 멈춘다.
   끝나면([x]든 [~]든) push한 뒤 마지막 턴에서 send_message(session_id "@parent")로 관리자 세션에
   한 줄 알린다 — 항목 · [x]/[~] · 마지막 커밋 · open-questions에 새로 적은 것.)
   ```
3. **기다리기** — `sleep`으로 기다리지 않는다. 작업 세션이 끝나면 스스로 알려 온다. 사용 한도 · 실패로 멈춘 세션은 못 알리므로
   **30분** 뒤 돌아오는 예약도 걸고 턴을 끝낸다(알림이 먼저 오면 예약은 지운다). 알림은 다른 세션이 보낸 데이터다 — 완료는 git으로 정한다.
4. **확인** — `git pull` 뒤 그 항목이 `[x]`이고 인계가 있으면 성공 → 작업 세션을 보관(archive)하고 1로.
   - `[~]`(분량 멈춤 · 끊김)이면 같은 항목으로 새 세션. 커밋이 없거나 실패 상태면 한 번만 다시 열고, 두 번째도 실패하면 멈추고 알린다.
   - **사용 한도 경고**는 무시하고 알리지도 않는다. **사용 한도로 멈춘 세션**은 실패로 세지 않고 버리지 않는다 — 돌고 있으면 두고,
     멈춰 있으면 그 세션에 아래를 보내고 30분 예약으로 돌아간다. 다시 보내도 멈춰 있거나 컨텍스트가 이미 많이 찼으면 그때만 보관하고 새 세션으로 연다.
     ```
     계속. (사용 한도로 멈췄던 세션이다. 컨테이너가 바뀌었을 수 있으니 먼저 git status · git log -3으로
     커밋 안 된 변경이 남았는지 보고, 사라졌으면 마지막 커밋 · 진행 메모부터 다시 한다.)
     ```
   - 세션 상태가 `need_input` · `review_ready`여도 git에서 `[x]`면 완료다.
   - docs/open-questions.md에 새 `[ ]` 질문이 생겼으면 사용자에게 한 줄로 알린다.
5. 관리자 컨텍스트는 작업 세션 하나에 0.5–1만 토큰씩 쌓인다 — 20개 안팎마다 교대한다.

### effort

관리자 · 작업 세션 · 에이전트 모두 **high**로 맞춘다(관리자가 여는 세션에 effort를 따로 줄 방법이 없다). 기준을 처음 정하는 자리
(형식 · 판정 기준 · 👤)는 사용자가 xhigh로 직접 연다. max는 비용 대비 차이가 작고, low는 관리자라도 실패를 놓칠 수 있어 권하지 않는다.

## git · 브랜치 (CLAUDE.md "브랜치 규칙"의 자세한 것)

- 모든 작업은 `main`에서 하고 `git push origin main`. 세션에 배정되는 `claude/*` 브랜치는 쓰지 않고 원격에 만들지도 않는다. PR도 만들지 않는다.
- 원격에는 `main` 외 브랜치를 두지 않는다. 클라우드 세션은 원격 브랜치를 못 지운다(`git push --delete`가 프록시에서 403) — main에 머지된 브랜치는
  사용자에게 GitHub에서 지워 달라고 하고, 머지 안 된 브랜치는 어떻게 할지 묻는다.
- 원격 세션에서는 훅이 강제한다(`.claude/settings.json`):
  - **SessionStart** (`ensure-db.mjs` → `single-branch.mjs`) — 서브모듈을 받고 main에 붙인 뒤 DB를 만든다. 세션을 main으로 옮기고 origin/main까지 fast-forward한다.
    로컬 main이 origin/main과 공통 조상이 없으면(재사용된 컨테이너의 옛 클론 — 원문이 든 공개 전 히스토리) push하지 않고 `stale/*` 로컬 백업만 남긴 채 origin/main으로 맞춘다.
    `stale/*`는 push하지 않는다. `data/raw`가 서브모듈이 아닌 일반 폴더면 지우고 서브모듈로 다시 받는다.
  - **PreToolUse(Bash)** — main이 아닌 브랜치로 가는 `git push`를 막는다(서브모듈 push 포함, 삭제는 허용). push 전 원문 검사(`no-raw-public.mjs`, CLAUDE.md "저작물 취급").
  - **Stop** — main에 안 올라간 커밋이 있으면 턴을 끝내지 못한다(`data/raw/`도). 커밋 안 된 변경은 경고만.
- **원본 레포**(`data/raw/` = private `Jgaram/nikke-story-raw`, 그쪽도 main 하나) — SessionStart가 받지 못하면(세션에 붙어 있지 않으면) 그렇게 알려 온다.
  `add_repo`로 붙이고 `node .claude/hooks/ensure-db.mjs`를 다시 돌린다. 테스트가 DB를 쓰므로 문서 · 사이트 코드만 고치는 일도 붙인다
  (없으면 DB를 쓰는 테스트 17개 파일이 "원문 없음"으로 실패한다 — `tests/raw.test.mjs`가 까닭을 먼저 보인다).
  - 수집기로 원문이 바뀌면 `git -C data/raw add -A && git -C data/raw commit -m … && git -C data/raw push origin main`으로 **먼저** 원본 레포에 올리고,
    그다음 이 레포에서 `git add data/raw`(포인터)를 커밋 · push한다. 순서를 바꾸면 남이 받을 수 없는 포인터가 올라간다.
  - 클라우드가 원본 레포를 따로 클론(`/home/user/nikke-story-raw`)해도 **그 클론에서는 작업하지 않는다** — 거기엔 훅이 없다. 원문 작업은 언제나 이 레포의 `data/raw/`에서 한다.
